# Marketing plan

## Purpose

Help SaaS teams check if Deployz can support a request to run their app in a customer's AWS account.

The main action is **Get Started Free**. The next product action is to connect GitHub and review the readiness report.

## Audience

| Priority | Audience | Trigger | Message | Next step |
| --- | --- | --- | --- | --- |
| 1 | Founder or technical lead at a small B2B SaaS team | A prospect asks for deployment in its AWS account | Use one process to install and update supported apps in customer AWS | Check app readiness |
| 2 | Independent SaaS developer | A larger customer asks for a dedicated installation | Test in your own AWS account before customer installation | Run a test deployment |
| 3 | AI app or agent team | A customer wants the app, database, and files in its account | Deploy a supported API and workers; check external model data flows separately | Check architecture support |

Qualify for one Linux x86-64 container image, an HTTP service, and a new VPC in AWS. Workers must use the same image. Check optional database and cache needs.

Do not target requests that require other clouds, on-premises servers, Kubernetes, GPUs, separate service images, or an existing VPC.

## Offer and message

Main message: **Deploy your SaaS into customer AWS.**

Offer: Free evaluation with readiness analysis, configuration, release builds, and one active test deployment per app in your own AWS account. No card or time limit. AWS resource charges still apply.

Paid plan in repository: USD 49 per month plus USD 19 per billable customer environment per month. Subscriptions start at USD 68 per month and include at least one billable customer environment. AWS costs are separate. Confirm prices before use.

## Channels

Start with founder posts on existing social accounts, direct replies to relevant requests, and individual prospect emails. Share the product sheet after a relevant conversation. Use the demo to show the actual steps.

Use community posts only where product posts are permitted. Identify your connection to Deployz. Answer the specific question before you share a link.

Do not start paid ads in this first cycle. First check which message brings teams with supported apps to evaluation. This is a test plan, not a forecast of demand.

## Four-week sequence

| Week | Work | Assets | Evidence to collect |
| --- | --- | --- | --- |
| 1 | Check claims, record demo, publish the core message | Product sheet, demo, social post 1 | Relevant replies, website visits, signup starts |
| 2 | Explain the installation process; contact relevant prospects | Social posts 2 and 3, prospect email 1 | Supported app needs, GitHub connections, report results |
| 3 | Answer cost and architecture questions; follow up where relevant | Social posts 4 and 5, prospect emails 2 and 3 | Test deployments, blockers, pricing questions |
| 4 | Explain release control; help active evaluators | Social post 6, evaluation emails | Successful tests, first customer installations, reasons for stopping |

Suggested workload: two social posts and up to five individually prepared prospect emails per week. Use fewer if the owner cannot give useful replies. Do not send the full sequence after a reply, an opt-out, or a clear lack of fit.

## Measures

Use this path: campaign visit → signup → GitHub connection → report completed → test ready → first customer environment ready.

Before launch, confirm which events are already recorded. The event names above describe business steps; they are not claims that tracking is installed. Use a manual weekly record if needed. Record counts and reasons for failure. Do not place code, secrets, or customer data in the tracker.

Calculate each step rate as completed next steps divided by eligible previous steps. Keep the same reporting period and cohort. If the denominator is zero, record N/A.

Use `utm_source`, `utm_medium`, `utm_campaign`, and `utm_content` on website links. Use `customer_aws_01` as the campaign name. Confirm that the site and signup flow retain attribution before relying on it.

At each weekly review:

1. Check whether replies came from the intended audience.
2. Check where supported apps stopped.
3. Change one message or one call to action.
4. Record the change and result.

Continue a message when it brings supported apps to evaluation. Revise it when it brings visits with little product fit. If reports show a product limit, state the limit clearly. Set numerical targets after the first week establishes a baseline.
